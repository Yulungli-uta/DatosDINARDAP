01 — Resumen

Qué se construyó y por qué

El análisis previo encontró credenciales de DINARDAP repetidas en texto plano en 3 archivos, sin control de versiones, y con manejo de errores inconsistente entre los 3 métodos públicos de la DLL. Esta fase implementó la arquitectura propuesta y aprobada.

El resultado son 4 proyectos dentro de una sola solución (DatosDINARDAP.sln): un gateway nuevo en .NET 9 que es el único que le habla SOAP a DINARDAP, un cliente HTTP moderno para sistemas nuevos, la DLL legacy reescrita por dentro (mismo contrato público, cero credenciales), y una suite de pruebas que fija el comportamiento de los 3 paquetes (Registro Civil, TCE, Títulos).

02 — Arquitectura

Flujo de una consulta, de punta a punta

Dos caminos conviven: el sistema legacy (izquierda) y un consumidor nuevo (derecha). Ambos terminan en el mismo gateway — DINARDAP solo ve una IP, la de WsUtaDinardap.Api.

El sistema legacy obtiene su propio token vía Client Credentials contra WsSegu (identidad técnica datosdinardap-legacy); un sistema nuevo reenvía el JWT del usuario o usa su propia identidad técnica. Ninguno de los dos habla SOAP directamente — eso vive únicamente en DinardapSoapGateway.

04 — Los 4 proyectos

Responsabilidad de cada uno

WsUtaDinardap.Api .NET 9 · se publica en el servidor. Único componente con credenciales/endpoint DINARDAP. Valida JWT localmente (JWKS de WsSegu) y autoriza por permiso.
DatosDINARDAP.Client .NET 9 · librería para sistemas nuevos. HttpClientFactory + Bearer inyectable. No sabe nada de SOAP ni de DINARDAP directamente.
DatosDINARDAP .NET Framework 4.8 · misma DLL de siempre para los sistemas institucionales actuales. Por dentro ahora llama HTTP a la API, no SOAP a DINARDAP.
WsUtaDinardap.Api.Tests xUnit · 24 pruebas sobre el mapeo de campos de los 3 paquetes y el enrutamiento del orquestador, sin red.

El único componente que sabe hablar SOAP

Todo lo demás pasa por IDinardapGateway. Agregar un paquete DINARDAP nuevo (116, 117…) no toca esta clase.

WsUtaDinardap.Api/Infrastructure/Dinardap/DinardapSoapGateway.csC#
public sealed class DinardapSoapGateway : IDinardapGateway
{
    public async Task<FichaGeneralDto> ConsultarAsync(
        string numeroIdentificacion, DinardapPackage paquete, CancellationToken ct)
    {
        var client = new InteroperadorClient(binding, new EndpointAddress(_options.Endpoint));
        client.ClientCredentials.UserName.UserName = _options.Username;   // desde entorno, nunca hardcodeado
        client.ClientCredentials.UserName.Password = _options.Password;
        // ... try/catch traduce TimeoutException/MessageSecurityException/CommunicationException
        // a DinardapException con código tipado — nunca deja escapar WCF crudo
    }
}

Ejecutado contra 10.102.12.83 / dbutasystem con tu aprobación. Todo aditivo (INSERT/MERGE), sin cambios de esquema, verificado por consulta después de correr el script.

Al verificar el mapeo AppAuth:ClientRoles en RepositoryUta/Configuration/appsettings.json se encontró ese bloque anidado por error dentro de Serilog:WriteTo[1] — en esa ruta nunca se leía, así que uta-signature tampoco recibía su rol ahí. appsettings.Production.json sí lo tenía bien ubicado (producción no estaba afectada). Se corrigió la posición y se agregó datosdinardap-legacy → R_DINARDAP_LEGACY en ambos archivos; RepositoryUta recompiló sin errores después del cambio.
